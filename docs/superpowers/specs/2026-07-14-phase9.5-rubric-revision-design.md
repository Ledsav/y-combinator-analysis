# Phase 9.5 Rubric Revision — Design

**Status:** Approved
**Date:** 2026-07-14
**Roadmap:** `documentation/plan_complexity_metric/roadmap.md` — resolves the deferred "Phase 9.5" decision flagged since Phase 7's "Open Question" and re-confirmed unresolved through Phases 8-10.

## Context

Since Phase 7, the Complexity Index has consistently missed two of the objectives doc's own success criteria:
- Correlation with log(team size): Pearson r = 0.035 (target: r > 0.2)
- Distribution spread: σ = 10.11 (target: σ ≥ 15)

Every phase since (7, 8, 9) confirmed this gap without acting on it, deliberately deferring the decision. Before this brainstorming pass, a diagnostic investigation was run against the real data to determine whether these targets are achievable through rubric tuning at all:

- **Team-size correlation**: no single raw feature (of the 8 Phase 6 features) correlates with log(team size) above r=0.193. Several technical-side features are *negatively* correlated (deep_tech_tag_count: r=-0.127) — in this dataset, deep-tech companies skew toward smaller teams, while large teams cluster around ops-heavy practical companies. Even an extreme 0%-technical/100%-practical reweight only reaches r=0.128. **No combination of current features clears r>0.2.**
- **Distribution spread**: 48.9% of companies score exactly 0.0 on `technical_score` (no deep-tech tags, no R&D-vocabulary keywords, no founder-background signal — most YC companies are plain software, not deep tech), and 56.3% cluster at `practical_score`=15.0 due to coarse ordinal/binary raw features (market type 0-3, regulated industry 0/1). Systematic testing of rebalancing/cap configurations found that σ≥15 is reachable only by nearly eliminating the technical dimension (e.g. a 15/85 split reaches σ=16.25 but contradicts the objectives doc's stated 50/50 "technical AND practical" design) or by exceeding the 0-100 bound in some configurations (invalid). A defensible, balanced rebalance tops out around σ≈12.

Both gaps share the same root cause: real "no signal" mass in the underlying feature data, not a tuning failure. This spec documents that finding and makes the corresponding rubric and target decisions.

## Decisions

1. **Relax the team-size correlation target.** Remove/relax the `r>0.2` team-size success criterion in the objectives doc. Document the diagnostic finding (no achievable feature combination clears it) as the rationale, not a silent removal.
2. **Moderate rubric rebalance for spread, target relaxed rather than fully met.** Shift the technical/practical split from 50/50 to **30/70** with moderately tighter caps (exact values below). This is a real, principled improvement (σ 10.11 → 11.95, +18%; team-size r 0.035 → 0.103 as a side effect, still short of 0.2) without gutting the technical dimension or breaking the 0-100 bound. The σ≥15 target itself is also relaxed in the objectives doc, with the same structural rationale documented.
3. **New formula (`src/etl/score.py` default parameters):**

   | Bucket | Cap (old → new) | Points (old → new) |
   |---|---|---|
   | `compute_deep_tech_score` | 3 → 2 | 20 → 12 |
   | `compute_description_score` | 3 → 2 | 15 → 9 |
   | `compute_founder_background_score` | 4 → 2 | 15 → 9 |
   | `compute_regulated_score` | — | 15 → 21 |
   | `compute_market_type_pts` (points per level) | — | 5 → 7 |
   | `compute_geo_ops_score` (intl cap/points) | 2 → 1 | 10 → 14 |
   | `compute_geo_ops_score` (ops cap/points) | 2 → 1 | 10 → 14 |

   Technical budget: 12+9+9 = 30. Practical budget: 21+21(=7×3 levels)+28(=14+14) = 70. Total = 100. Verified against real data: mean=27.36, median=25.5, std=11.95, p75=35.0, p90=42.0, p95=48.0, max=85.0, 51 companies score exactly 0.
4. **New versioned output, v1 preserved.** `data/processed/scores/complexity_index_v2.csv`, generated via the existing `scripts/run_complexity_pipeline.py --output-version v2` (no pipeline code changes needed — this flag already exists from Phase 8). `complexity_index_v1.csv` stays committed as the historical Phase 7 baseline; nothing deletes or overwrites it.
5. **Full downstream regeneration against v2** (explicit scope decision — a smaller "v2 file only" option was considered and rejected in favor of keeping all analysis artifacts consistent with the current rubric):
   - `notebooks/complexity_analysis.ipynb` (`scripts/generate_complexity_analysis_notebook.py`) re-pointed at `complexity_index_v2.csv` and re-executed — every real number in it changes (batch trend, status/industry breakdowns, correlation heatmap, validation questions, top/bottom 25, Findings text).
   - The dashboard (`scripts/generate_dashboard.py`) re-pointed at v2, output renamed `output/complexity_dashboard_v2.html` (matches the new score version), with its Key Findings bullets rewritten against v2's real numbers.
6. **New dashboard section: "About This Index"**, placed after the title and before Key Findings — explains what the score measures, how it's computed (capped linear scaling, v2's 30/70 weighting and why), key assumptions (deep-tech signal is tags+keywords not a technical audit; "regulated" is industry-based not a legal determination; team size isn't part of the formula since it wasn't found predictive), how to interpret a score (bands derived from v2's real distribution: **0-20 minimal**, roughly bottom quartile; **20-40 moderate**, the bulk of companies including the median at 25.5; **40+ high**, roughly the top 10%, p90=42), and one honest paragraph on the known limitations (Decisions 1-2, plainly stated, not buried).
7. **Objectives doc updates** (`documentation/plan_complexity_metric/objectives_and_metrics.md`): update section 2.1/2.2's "Weight: 50%" headers to reflect the new 30/70 split; update the "Distribution/Variance" row (σ≥15) and the `teamSize` sanity-check row (r>0.2) in the success-metrics tables to reflect Decisions 1-2, with the diagnostic rationale recorded inline (not just cross-referenced).
8. **Roadmap update**: insert a completed "Phase 9.5: Rubric Revision" entry between Phase 9 and Phase 10 (renumbering Phase 10→11, 11→12 in both `roadmap.md` and `roadmap_todo.md`), closing out the decision that's been open since Phase 7.

## Architecture

No new modules. This is a parameter change to existing, already-tested functions:
- `src/etl/score.py`: only the *default* values of `compute_deep_tech_score`, `compute_description_score`, `compute_founder_background_score`, `compute_regulated_score`, `compute_market_type_pts`, `compute_geo_ops_score`'s keyword arguments change — all six functions' logic, signatures, and existing unit tests (which pass explicit non-default values to test scaling behavior independent of the curated constants, per Phase 6/7 convention) are unaffected. `build_score_table`, `validate_scores`, `run_scoring_pipeline` are unchanged.
- `scripts/generate_complexity_analysis_notebook.py`: only the `SCORES_PATH`-equivalent literal (`data/processed/scores/complexity_index_v1.csv` → `..._v2.csv`) changes in the setup cell; every other cell's code is unchanged (same functions, same logic) — only the *executed output* changes because the input data changed. The Findings markdown cell (Task 6 of the original Phase 9 plan) gets rewritten with fresh real numbers.
- `scripts/generate_dashboard.py`: `SCORES_PATH` updated to v2; `OUTPUT_PATH` updated to `complexity_dashboard_v2.html`; a new `build_about_section() -> str` function added (parallel to the existing `build_findings_summary()`), wired into `build_dashboard_body()` right after the `<h1>` and before the (rewritten) findings summary; `build_findings_summary()`'s bullet content rewritten with v2's real numbers.

## Testing

- No new unit-testable logic beyond `build_about_section()` (a static-content function, tested the same way `build_findings_summary()` already is — presence of key section markers/stats, per the existing Phase 10 test pattern).
- `src/etl/score.py`'s existing test suite (all tests pass explicit parameter values, none depend on the changed defaults) requires no test changes — this is the acceptance check that the six functions' *logic* wasn't touched, only their curated constants.
- Acceptance for the regenerated notebook/dashboard follows the same bar Phases 9-10 already established: `jupyter nbconvert --execute` exits 0 with real output in every cell; the dashboard's structural checks (single Plotly bundle, all chart divs present, valid JSON company records) re-run against the v2-generated file.

## Out of Scope

- Any change to Phase 6's feature-engineering logic (e.g. fixing `founder_phd_count`'s near-zero variance) — still a documented, separate limitation.
- Reopening percentile/rank-based normalization (explicitly considered and rejected — would hit any target σ by construction but abandons the interpretable capped-linear-scaling design Phase 7 committed to).
- Deleting or archiving `complexity_index_v1.csv`, `complexity_dashboard_v1.html`, or the v1-analyzing content already in `notebooks/complexity_analysis.ipynb`'s git history — v1 remains the historical record of the original calibration.
- Any further tuning pass beyond the single documented rebalance in Decision 3 — if v2's numbers still don't satisfy someone reviewing this later, that's a new brainstorming pass, not silently re-tuned here.
