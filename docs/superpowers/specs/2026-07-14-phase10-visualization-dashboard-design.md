# Phase 10 Visualization Dashboard — Design

**Status:** Approved
**Date:** 2026-07-14
**Roadmap:** `documentation/plan_complexity_metric/roadmap.md` — inserted as the new checklist item 10 ("Visualization Dashboard"), pushing the existing item 10 ("Documentation & Reproducibility") to item 11.

## Context

Phase 9 (`notebooks/complexity_analysis.ipynb`) validated `data/processed/scores/complexity_index_v1.csv` (4,844 companies) with static matplotlib charts and a manually-reviewed outlier table, but a notebook is not a good tool for someone who wants to explore results interactively — filter to a batch, search for a company, or hover a chart for exact values. Phase 10 builds a standalone HTML dashboard for exactly that: exploring the already-computed index, not recomputing or re-validating it.

## Decisions

1. **Static, self-contained HTML — no server.** A single file, `output/complexity_dashboard_v1.html`, generated by `scripts/generate_dashboard.py`. Opens directly in a browser from disk. Rejected alternative: a live Streamlit/Dash app — more dynamic, but requires a running process and a new class of runtime dependency; not needed since the underlying data doesn't change between dashboard views.
2. **All assets bundled inline — no CDN.** Plotly.js is embedded directly in the HTML (not loaded from a CDN URL), so the dashboard works fully offline and isn't subject to a CDN's future availability or version changes. Matches the project's existing "100% deterministic / reproducible" ethos (objectives doc).
3. **Two independent sections, not cross-filtered.** (a) A set of aggregate Plotly charts mirroring Phase 9's notebook analysis, each independently interactive (hover/zoom/pan) via Plotly's own built-ins. (b) A separate company-explorer table with its own sort/filter/search. The table's filters do **not** drive the charts, and vice versa. Rejected alternative: full cross-filtering (selecting in the table updates the charts) — a substantially larger engineering effort (state management between a custom table and multiple Plotly figures) for a first version whose primary need is "let me look at the analysis and let me look up companies," not a fully linked BI tool. Revisit in a future phase if the static split proves insufficient.
4. **Company table: hand-rolled vanilla JS, no table library.** Company data is embedded as a JSON array in a `<script>` tag; plain JS renders an HTML `<table>`, handles click-to-sort headers, dropdown filters, and free-text search. Rejected alternative: DataTables.js (jQuery plugin) — more built-in features (pagination, multi-column sort) but adds a jQuery dependency and more inline-bundled JS for features not needed at this scale (4,844 rows, single-column sort, three filter dimensions).
5. **No pagination in the table's first version.** All 4,844 rows render as plain `<tr>` elements; filtering hides rows via `display:none` rather than re-rendering a paginated view. This is expected to perform fine in modern browsers at this row count. If real-browser verification during implementation shows otherwise, pagination is the fallback — flagged here rather than pre-built speculatively (YAGNI).
6. **New dependency: `plotly`.** Added to `requirements.txt`. First new dependency since Phase 8 (`jupyter`, `nbconvert`, `scipy`, `matplotlib`).
7. **Verification without a browser tool.** Since there's no unit-testable business logic (same situation as Phase 9's notebook), acceptance is: (a) an automated structural-content check script — regex/string-based, no new library — confirming the file exists, contains exactly one inline Plotly.js bundle (not duplicated per chart), has all 6 expected chart divs, and the embedded company JSON has exactly 4,844 records with a few spot-checked values matching `complexity_index_v1.csv`; (b) a manual visual pass by the person/agent implementing this, using an actual rendered browser view of the generated body content before calling the work done — matching the project's "verify UI changes in a browser" expectation, adapted for a file:// artifact rather than a dev server.

## Data Sources & Joins

- `data/processed/scores/complexity_index_v1.csv` — base table (all scores, batch, status).
- `data/processed/step3_enriched/industries_enriched.csv` — industry chart (exploded, ≥20-company threshold, same treatment as Phase 9's `industry_merged`) and the table's per-company industry list (aggregated back to one comma-joined string per company id for the table — a different aggregation direction than the chart's explode, done separately for each use).
- `data/processed/step3_enriched/companies_enriched.csv` — `teamSize`, joined on `id`, shown as a table column for context (no team-size chart in this phase — Phase 9 already covers that correlation numerically; not duplicated here as a chart).
- `data/processed/features/complexity_features.parquet` — the 8 raw features, needed for the correlation heatmap (same 17-column set as Phase 9's heatmap: 8 raw features + 6 bucket scores + 3 top-level scores).

## Architecture

```
scripts/generate_dashboard.py
├── build_dashboard_body(scores_df, industry_df, features_df, companies_df) -> str
│     # Body-only HTML: <style>, chart <div>s (each populated via Plotly's
│     # to_html(full_html=False)), one shared inline Plotly.js bundle
│     # (injected once, not per chart), the company table's JSON payload
│     # and its sort/filter/search <script>. No <html>/<head>/<body> tags —
│     # this return value is also usable standalone for a rendered preview.
├── build_standalone_dashboard(body: str) -> str
│     # Wraps `body` in a minimal <html><head><title>...</title></head>
│     # <body>...</body></html> shell — this is what gets written to disk.
└── main() -> None
      # Reads the 4 data sources, calls build_dashboard_body then
      # build_standalone_dashboard, writes output/complexity_dashboard_v1.html
```

**Charts** (all Plotly, hover-interactive):
1. Score distribution — histogram of `complexity_score`
2. Technical vs Practical — scatter, hover shows company name
3. Complexity by batch — line, chronological (Winter before Summer within a year, same convention as Phase 9)
4. Complexity by status — bar, mean `complexity_score` per status
5. Complexity by industry — bar, exploded industries with ≥20 tagged companies
6. Correlation heatmap — 8 raw features + 6 bucket scores + 3 top-level scores

**Company Explorer table columns:** id, slug, name, batch, status, industries (comma-joined), teamSize, technical_score, practical_score, complexity_score. Click-to-sort on any column (ascending/descending toggle); dropdown filters for batch, status, industry (options populated from the actual data); free-text search box filtering on company name.

## Output

- `output/complexity_dashboard_v1.html` — the deliverable, self-contained, offline-capable.
- `scripts/generate_dashboard.py` — the generator, run via `./.venv/Scripts/python.exe scripts/generate_dashboard.py`, following the same generator-script convention as `scripts/generate_score_design_notebook.py` and `scripts/generate_complexity_analysis_notebook.py`, adapted for a plain-HTML artifact instead of a notebook.
- `requirements.txt` gains `plotly`.
- Roadmap checklist item 10 (new) marked complete; the former item 10 ("Documentation & Reproducibility") renumbered to item 11, with its scope expanded to include documenting the dashboard's usage.

## Out of Scope

- Live cross-filtering between the table and the charts (Decision 3).
- A live Python web app / server (Decision 1).
- Pagination (Decision 5 — deferred unless real-browser testing shows a need).
- Recomputing or re-validating the index — this phase only visualizes `complexity_index_v1.csv` as-is; any rubric revision remains the deferred "Phase 9.5" decision from Phase 9.
- A team-size chart (already covered numerically in Phase 9; `teamSize` appears only as a table column here for context).
