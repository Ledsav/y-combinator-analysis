# Phase 13: Static Marketing/Analysis Site (Landing, Dashboard, Pipeline)

**Date:** 2026-07-15
**Status:** Design approved, not yet implemented

---

## 1. Motivation

The project has a working, config-driven Complexity Index (Phase 12) but no presentation layer built to be *looked at* by someone who isn't running the pipeline themselves. The existing `output/complexity_dashboard_v2.html` is a functional, single-file Plotly dashboard generated by `scripts/generate_dashboard.py` — useful as a working artifact, but it reads as an internal QA tool (default Plotly styling, flat bullet-list findings, a full raw-feature correlation matrix) rather than something built to explain the project's actual insight to a reader.

This phase adds a three-page static site — a landing page, a redesigned dashboard, and a page explaining how the ETL pipeline (including the Phase 12 config-driven scoring engine) actually works — hosted on GitHub Pages. It sits alongside the existing pipeline as a presentation layer only: no changes to `src/etl/`, `scripts/generate_dashboard.py`, or `scripts/generate_complexity_analysis_notebook.py`, and no scores are recomputed.

**Not in scope:** any change to scoring logic, the ETL pipeline itself, or the existing versioned dashboard/notebook artifacts. Those keep working exactly as documented in the README.

## 2. Architecture

### 2.1 Stack

Hand-authored static site — plain HTML/CSS/JS, no framework, no bundler, no build step. Three pages share one CSS file and a small set of JS modules.

```
site/
├── index.html            # Landing
├── dashboard.html         # Redesigned dashboard
├── pipeline.html           # ETL architecture + scoring-engine diagrams
├── assets/
│   ├── style.css           # Shared design system (tokens + components)
│   ├── nav.js                # Shared header/nav behavior
│   ├── charts.js               # D3 chart-building functions, reused across dashboard
│   └── fonts/                    # Self-hosted woff2 (Fraunces, IBM Plex Sans, IBM Plex Mono)
└── data/
    ├── companies.json          # Per-company records: id, slug, name, batch, status,
    │                             industries, teamSize, technical_score, practical_score,
    │                             complexity_score — dashboard scatter + explorer table
    ├── summary.json             # Pre-aggregated: score distribution bins, mean by batch,
    │                             mean by status, mean by industry (top/bottom), trimmed
    │                             correlation matrix (bucket scores + totals only), headline
    │                             stats for landing (count, median, sigma, top industry)
    └── pipeline.json              # Structured description of the 5 ETL steps (module,
                                     input/output dirs) and the 7 rubric buckets (name,
                                     dimension, raw_feature/combine, method, params) read
                                     from config/rubric_v2.yaml — feeds diagram labels;
                                     diagram geometry itself is hand-coded SVG, not
                                     generated from this file
```

### 2.2 Data export

One new script, `scripts/export_site_data.py`, reads the already-computed `data/processed/scores/complexity_index_v2.csv`, `data/processed/features/complexity_features.parquet`, `data/processed/step3_enriched/{industries,companies}_enriched.csv`, and `config/rubric_v2.yaml`, and writes the three JSON files above into `site/data/`. It performs no scoring or recomputation — it's a read-and-reshape step, run manually (like `generate_dashboard.py` today) whenever the underlying CSV changes. NaN values are converted to `null` (JSON-safe), following the existing pattern in `generate_dashboard.py`'s `build_company_records`.

### 2.3 Deploy

`.github/workflows/deploy-pages.yml`: on push to `master` touching `site/**`, publishes the `site/` directory via `actions/deploy-pages` (no build step — the directory is already what gets served). Enabling Pages itself (Settings → Pages → Source: GitHub Actions) is a manual one-time repo-settings step the user does themselves.

## 3. Design system

**Direction:** "Field Report" — an equity-research/lab-notebook register: quantified and data-forward, not a lifestyle-magazine look. Deliberately avoids the generic cream-background + terracotta-accent serif look genAI defaults to.

**Color:**
| Token | Hex | Use |
|---|---|---|
| `paper` | `#FBFAF6` | page background |
| `ink` | `#1B1B18` | primary text |
| `ink-muted` | `#5C594F` | secondary text |
| `technical` | `#2B4C7E` (denim blue) | Technical dimension, everywhere |
| `practical` | `#C08A2E` (ochre gold) | Practical dimension, everywhere |

No third "brand" accent — `complexity_score = technical_score + practical_score`, so the palette mirrors the data model instead of adding a decorative color. The correlation heatmap's diverging scale reuses this exact pair with a neutral gray midpoint; the industry-ranking bar's sequential scale uses a single ink-gray ramp. Final hex values run through `dataviz`'s `validate_palette.js` (light mode) before shipping — this spec fixes the direction, not the validated-final values.

**Type:**
- Display serif **Fraunces** — headlines and narrative voice only, used sparingly at large sizes.
- Body **IBM Plex Sans** — all running text.
- Data/numerals **IBM Plex Mono** — every score, stat, and label, so data always reads visually distinct from prose.

**Signature element — the split-bar readout:** a horizontal bar, denim segment (technical) + gold segment (practical), total in Plex Mono beside it. Repeated everywhere: the nav mark, landing stat tiles, every row of the company explorer, and as the literal visual grammar of the pipeline's scoring-engine diagram (buckets → dimension bars → total). It is a drawing of the actual scoring model, not decoration.

**Accessibility floor:** responsive to mobile widths, visible keyboard focus states, `prefers-reduced-motion` respected, categorical/diverging colors validated for CVD separation, a table-view fallback available for the correlation heatmap.

## 4. Page specs

### 4.1 Landing (`index.html`)

- **Hero:** eyebrow label ("A REPRODUCIBLE STARTUP COMPLEXITY INDEX", Plex Mono), Fraunces headline, one-sentence subhead on the two dimensions. No hero chart — the stat tiles below carry that job.
- **Headline stats row:** 4 split-bar-styled tiles from `summary.json` — companies scored, score range/median, technical-vs-practical independence (r≈−0.05, stated as a current fact), top-scoring industry.
- **Narrative teaser:** two columns — prose (what the index measures and why practical execution is weighted more heavily than raw technical difficulty, as a property of the current model, not a change from an earlier one) beside a small static technical-vs-practical scatter as a dashboard preview.
- **Nav cards:** two ticket-stub-styled links to Dashboard and Pipeline, each stating in one line what the reader will find there.
- **Footer:** GitHub repo link, generation timestamp from `summary.json`.

### 4.2 Dashboard (`dashboard.html`)

- **Hero KPI row:** total scored, median complexity, σ (spread), top industry.
- **Chart sections, narrative-ordered** (each has a one-sentence headline insight above the chart, replacing the current flat bullet-list findings):
  1. **Score distribution** — histogram, annotated with median/p90 lines and shaded 0–20/20–40/40+ bands.
  2. **Technical vs. Practical** — scatter, annotated for near-zero correlation with light quadrant labels.
  3. **Complexity by industry** — horizontal ranked bars, top 5 + bottom 5 only, direct-labeled.
  4. **Complexity by batch** — line chart, annotated with the observed rise across batches (stated as current shape of the data, no "increased from Phase X" framing).
  5. **Complexity by status** — compact 4-bar comparison, direct-labeled.
  6. **How the pieces relate** — correlation heatmap trimmed to the 7 bucket-scores + 3 dimension/total scores (drops raw feature columns), with standout cells direct-labeled; a table-view toggle is available.
- **Company Explorer:** same search/filter/sort behavior as today's table, rebuilt so each row's three score columns collapse into one split-bar readout cell instead of three plain numbers.

All chart forms, color assignments, and interaction (tooltips, legends, filters) follow the `dataviz` skill's procedure — form chosen by the data's job, color assigned last, hover layer by default, direct labels selective not exhaustive.

### 4.3 Pipeline (`pipeline.html`)

- **Intro:** one short paragraph — this page shows how the number is computed.
- **Diagram 1 — ETL flow:** five connected stage-cards (clean → impute → enrich → features → score), each showing its module, input/output directory. The `enrich` card is visually marked as opt-in (dashed border, "off by default" tag) as a description of current pipeline behavior. Arrows fan from `score` into its outputs (CSV, notebook, this site).
- **Narrative bridge:** one sentence — the `score` step is config-driven: its rubric lives in a YAML file the engine reads, not in code.
- **Diagram 2 — scoring engine internals:** the 7 rubric buckets (left) → combine step (`identity`/`weighted_sum`) → scaling step (`linear_capped`, cap→points) → `<bucket>_score` → grouped into dimension totals (denim/gold) → `complexity_score` split-bar.
- **Marginal callout — "Adding a new scoring method":** the engine's actual extension contract (write a function honoring the `[0, points]` scaling contract, register it in `scaling.py`, reference it from a rubric YAML) as a factual description of what's implemented today.
- **Why YAML:** one short paragraph — inline comments preserve the rationale behind each cap/points value, as a property of the current config format.
- **Known limitations:** stated as current facts, plainly — `enrich` must be explicitly included for `features` to see freshly-enriched data; team-size correlation is weak (r≈0.10) because roughly half the dataset carries no deep-tech signal at all.

All copy across all three pages describes current values and current rationale only — no phase numbers, no "revised from," no before/after framing anywhere on the site.

## 5. Testing & verification

1. `scripts/export_site_data.py` gets unit tests (following the existing `tests/` pattern): correct row counts, NaN→null conversion, correct aggregation math in `summary.json` (spot-checked against values already verified in the notebook), rubric buckets in `pipeline.json` matching `config/rubric_v2.yaml`.
2. Palette validated with `dataviz`'s `scripts/validate_palette.js` before any chart ships.
3. Manual browser verification (per the `verify` skill) of all three pages: golden-path nav between pages, table search/filter/sort, chart tooltips/hover, responsive check at mobile width, keyboard focus visibility.
4. GitHub Actions workflow verified by pushing to a branch/PR and confirming the Pages deploy succeeds before merging to `master`.

## 6. Out of scope (explicitly deferred)

- Any change to `src/etl/`, scoring logic, or rubric values.
- Any change to the existing `scripts/generate_dashboard.py`, `scripts/generate_complexity_analysis_notebook.py`, or the versioned `output/complexity_dashboard_v1.html`/`v2.html` artifacts — they remain as historical/reproducibility artifacts, untouched.
- Dark mode as a shipped feature (tokens are structured to support it later, but this phase ships light mode only).
- A CMS, server, or any dynamic backend — the site is fully static.
